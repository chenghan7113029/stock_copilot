## 0.0 先分类，再分层：判别四问（2026-11-15 Owner 裁决）

> **本节是总闸。** §1 的五层只回答「一条知识进了库以后按什么形态管」；**要不要进库由本节决定**。
> 两者不是同一件事，混用会重演「把配置、逻辑、知识摆成一个维度」的错误（Owner 2026-11-15 指正）。

### 四问（按序问，第一个命中即定归属）

```text
Q1 只有这一次才有值吗？（某个股票代码、今天的持仓、某次时间窗）        → 是：入参
Q2 所有问题走同一套步骤或算法吗？（MA 周期、MACD 12/26/9、DCF 展开）   → 是：固有逻辑
Q3 是「业务上什么算对」的标准，且业务方不发版就能改、改完为结论负责？    → 是：知识
Q4 说不清谁负责？                                                      → 负债（登记 + 指派，不假装有知识）
```

顺序有讲究：Q1 最便宜（一次性值一眼可辨），Q2 次之（代码里所有问题都走它 = 算法），
剩下的才轮到 Q3 的拷问「谁改、改完谁负责」。**Q3 的核心是"不发版就能改"**——知识变更不需要
软件发版，只需要 Owner 一句话，所以它的闸门是 Owner 背书，不是代码评审。

**四种归属的治理完全不同：**

| 归属 | 谁守 | 怎么改 | 怎么验 | 错了的后果 |
| --- | --- | --- | --- | --- |
| 入参 | 采集方（适配器/用户） | 随时 | schema + 时效校验 | 数据脏，口径没错 |
| 固有逻辑 | engineer + architect | 改代码，走 specs + tests | 单测 / `openspec validate` | 实现 bug |
| 知识 | **业务 Owner** | Owner 一句话（留痕），不改代码 | 能指向一次可复算的核对 / 判例复现 | 判断标准错，**所有结论都错且看不出来** |
| 负债 | 已指派的 assignee | 到期二选一：定义成知识，或降为假设 | 台账有 assignee + due | 假装是知识 → 静默错误 |

### 本设计（§1 五层）与这条轴的差异 —— 必须承认的四条

| 现有层 | 按四问重判 | 处置 |
| --- | --- | --- |
| `canon` 里的**不可调不变量**（T+1、封板顺延、无未来函数） | Q2 是（市场规则，所有问题一样） | **固有逻辑**：留在代码常量 / specs，知识库只留指针，不条目化 |
| `rules` 里的**纯算法要求**（block bootstrap 报什么、部分池化怎么做） | Q2 是 | **固有逻辑**：§4.1 已把它落 `代码 + 单测`，知识条目只保留「业务上为何必须这么算」一句 |
| `facts` 现状事实（三源 K 线都不是后复权…） | 四问无出口（它是「现在是什么」，没人对它负责业务判断） | **现状索引**，不是知识 → 迁 `docs/design/`（下一波） |
| `cases` 裁决与实验结论 | 是知识**达成过程的证据**，不是当前有效知识 | **证据** → 迁 `docs/cases/`，结论提炼成 `canon`/`rules` 条目并 `registry_refs` 回指（下一波） |
| `canon` 的业务口径 / 阈值 / 枚举 | Q3 是 | **知识**（保留） |
| `hypotheses` 未确认 | Q4 | **负债**（保留，但分账见下） |

**负债分账（一张台账，两种处置）：**

- `known_unknowns.yaml` 的 `kind: unanswered` —— 等业务方答复的「什么算对」，处置 = 问人；
- `known_unknowns.yaml` 的 `kind: unowned_value` —— 有生效值、系统在跑，但没人认领这个值是业务标准，
  处置 = 指派认领；到期未认领 → 整组降为 `假设`，不得当确定口径引用。

## 0. 为什么需要五层（一句话）

本仓库的知识线有三条独立约束，任何单层方案都会在其中一条上失效：

1. **知识不可发明**（`config/knowledge/README.md:21`）：置信度必须可机检 → 需要「未确认」与「已确认」在结构上分开，否则只能靠 `confidence` 一个字段打补丁。
2. **代码现状 ≠ 正确口径**（`config/knowledge/README.md:23`）：仓库里大量「现在是什么」的事实（例如「三源 K 线取数都不是后复权」）**必须能被记录，又不能被当成口径** → 需要独立的事实层，且它的退役驱动力是「代码改了」，不是「口径变了」。
3. **知识跨波存活、持续升降级**（`config/knowledge/README.md:4`）：口径会因监管/费率/业务裁决而变，所以每条知识都必须能「降级、被取代、退役」而不删除 → 需要能表达生命周期，而不是只有置信度。

五层 = 「确认后的两种形态（口径 / 方法）」+「事实」+「未确认」+「裁决与结论」，对应角色文件里的「强度 × 频次」四象限再加一格事实层。

## 1. 知识分层（5 层）

### 1.1 总览

| 层 | 目录 | 一句话语义 | 强度 | 频次 | 允许的 `confidence` | 数量预期 |
| --- | --- | --- | --- | --- | --- | --- |
| `canon` 口径层 | `config/knowledge/canon/` | **必须等于/落在某个值**：口径、参数、阈值、日期、枚举（可用一个标量表达） | 硬规则 | 高 | `确定` | 少（几十条级），每条都被多条需求/实验消费 |
| `rules` 规则层 | `config/knowledge/rules/` | **做某件事必须按某个算法或流程**：方法、步骤、判定顺序 | 硬规则 | 中/低 | `确定` | 中（方法条目，随能力增长） |
| `facts` 事实层 | `config/knowledge/facts/` | **本仓库现在是 X**：可 grep 复核的现状（代码 / 规格 / 配置 / 数据可得性） | 硬规则（仅「现在是什么」） | 低 | `确定` | 中，且淘汰最快（代码一改即退役） |
| `hypotheses` 假设层 | `config/knowledge/hypotheses/` | **尚未确认**：待 Owner 答复的口径、外部方法参数、软标签登记、候选阈值 | 软启发 | 中/高 | `假设` | 多，是「知识负债的正面形态」 |
| `cases` 判例层 | `config/knowledge/cases/` | **已经裁决过**：信源冲突怎么裁的、实验得出什么结论、哪个方案被否及理由 | 软启发（可引为约束） | 低 | `确定` / `假设`（随裁决依据） | 少，冷存储、探索检索 |

> 「强度」定义（角色文件口径）：**硬规则 = 违反即 bug**（代码/流程必须照做，违反要被测试或评审打回）；**软启发 = 参考建议**（可用于解释、排序、起草，不可作为唯一依据）。
> 「频次」是**运行时属性**，不是设计时拍脑袋 → 度量方法见 §3.1。

### 1.2 每层语义详解（含「什么不属于本层」）

#### `canon` 口径层

- **准入**（三条全满足）：① 能被**一个标量 / 枚举 / 日期 / 阈值**表达（判据：能不能写成配置里的一个 key）；② 有权威来源（人工答复或仓库一手材料原文）；③ 有**可回解的消费点**（2026-11-15 修订：原「≥2 条 Requirement」改为分档门槛，理由见下方修订说明）：
  - **消费点定义**（满足任一即计 1 个）：ⓐ 一条 Requirement —— 写进 `requirement_refs`，且该 Requirement 的正文或 Scenario 提及该口径；ⓑ 一条 spec Scenario 断言该口径 —— 与所属 Requirement **分别计数**（Scenario 是独立、可机检的断言）；ⓒ 一次已验证实验 —— 写进 `registry_refs`；ⓓ 上位约束 —— 被 ≥1 条 canon 条目的 `notes` / `scope_note` 反向引用。
  - **分档门槛**：**强口径**（取值错误会改变金额 / 比例 / 是否执行（拒绝、顺延、门禁）/ 判定结论）→ **≥2 个消费点**，或 **1 条 Requirement + 该 Requirement 下 ≥1 条 Scenario 断言**；**低风险配置项**（只影响提示文案 / 枚举展示 / 数据校验 / 日志，不进入金额与判定）→ **≥1 个消费点**。
  - **观察名单（唯一例外通道）**：强口径因下游 spec 尚未落地而只有 1 条 Requirement、且无 Scenario 断言时，可暂入 canon，但 `notes` MUST 写「观察名单（无 Scenario 断言）」并写清消费点；连续 **2 波**无新增消费点 → 降 `hypotheses`；观察名单条目不得被实现当作强口径引用（须先补 spec Scenario）。同一波新增 canon 的观察名单占比 **>1/3** → K1 须在收波报告复核门槛本身（防例外架空规则）。
  - **无消费点 → 不新建 canon**：先落 `hypotheses` / `known_unknowns.yaml`（§1.4）。
- **典型内容**：复权口径（后复权 / 分段复权）、T+1、封板顺延、公告日对齐与保守回退日、三段样本年份、每组 ≥30 只、组数 9–27、共线合并 0.7、MA60 定义、K 上报要求、基准双口径。
- **不属于本层**：需要一段算法才能落地的东西（→ `rules`）；「代码里现在写的是 qfq」（→ `facts`）；等着 Owner 答复的费率数值（→ `hypotheses`）。

#### `rules` 规则层

- **准入**：① 需要**多步流程或算法**才能落地（判据：要写成一个函数/流程而不是一个 key）；② 有权威来源；③ 至少被 1 条 Requirement 或 1 个已验证流程消费。
- **典型内容**：block bootstrap / cluster-robust 的选择与报告要求、部分池化（向组均值收缩 + 输出组内分位）、分组有效性比值、三分位 × 三分位组合爆炸控制、软标签登记流程、三级门禁状态机、预注册与烧毁的流程语义。
- **不属于本层**：单一阈值（→ `canon`）；未确认的方法参数（→ `hypotheses`）。

#### `facts` 事实层

- **准入**：① 主语句形如「本仓库现在是 X」；② **能被一条命令/grep 复核**（必须在条目里给出可复核的位置：文件:行 或 规格锚点）；③ 与某条 Requirement 有明确关联（否则不采集，避免囤无关事实）。
- **典型内容**：三源 K 线取数都不是后复权（tushare/akshare 明写前复权，baostock 传 `adjustflag="2"`）、K 线表无成交额列、财务快照无公告日且报告期语义混用、仓库的「涨跌停」只是市场广度近似、交易日判断 V1 只有「工作日 + 可配置休市日」且当前休市表为空、总市值/股息率为无时点单值。
- **不属于本层**：「应该怎么做」（→ `canon`/`rules`）。**本层条目永远不能被当作口径引用**：它的用途是解释「为什么现在做不到」，以及给评审一个可复核的锚。
- **退役驱动力**：代码/规格改了 → 旧条目 `retired`，按需新增新事实条目（不要就地改语义，见 §4.4）。

#### `hypotheses` 假设层

- **准入**：① 有**推断来源**（人工答复未到、`ref/` 快照、外部资料、本波识别出的空白）；② 明确写「待谁确认 / 何时复核」（`review_at` 或 `unknown_ref`）；③ 不得作为唯一依据驱动代码行为。
- **三类典型内容**：① **待口径答复**（费率、税率、切点基准、门禁阈值、块长、收缩强度）；② **软标签登记**（主题 / 产业链 / 管理层评价，含「标签 + 时间 + 理由」，用于半年后回看 60 日超额）；③ **候选参数**（外部方法参数、ref 借鉴来的做法）。
- **不属于本层**：已裁决的结论（→ `cases`）；无任何推断来源的「拍脑袋」（→ 不入库，进 `known_unknowns.yaml`）。

#### `cases` 判例层

- **准入**：① 有**裁决主体与时间**（Owner 答复、信源优先级裁决、实验台账记录）；② 能说明「这个裁决约束了哪条 Requirement / 哪个设计选择」；③ 结论类条目必须带 `registry_refs`（指向实验台账 ID）。
- **典型内容**：信源冲突裁决（后复权 vs 现行前复权规格；公告日 vs 报告期；涨跌停近似量不可用于撮合）、判例原理（前复权为何产生假信号）、被否方案（本文件 §5 的分层方案也在此留档）、实验结论（校准通过/失败、某规则有效/无信号）、路线（校准通过后依次测什么）。
- **不属于本层**：还在等答复的推断（→ `hypotheses`）；可被一个 key 表达的规则（→ `canon`）。

### 1.3 「一条知识进哪层」判定流程（不许靠感觉）

按顺序问，**第一个命中即定层**：

```text
0) 有任何来源吗？（人工答复 / 仓库一手材料 / 可复核现实）
     无 → 不入库，交 K2 记 config/knowledge/known_unknowns.yaml
1) 主语句是「本仓库现在是 X」，且能用一条命令复核？
     是 → facts
2) 现在只能标「假设」（未答复 / 只有 ref / 外部资料）？
     是 → hypotheses
3) 是「已裁决的冲突 / 实验结论 / 被否方案」，且有裁决主体与时间？
     是 → cases
4) 能表达成一个标量 / 枚举 / 日期 / 阈值（=配置里的一个 key）？
     是 → canon
5) 需要一段算法或多步流程才能落地？
     是 → rules
（0–5 全不命中 → 说明这条知识还没想清，按「不入库」处理并报 K1）
```

**边界案例（用回测的真实条目校验这套流程）**

| 例子 | 判定路径 | 结果 | 为什么不是别的层 |
| --- | --- | --- | --- |
| 「回测价格必须后复权」 | 0 有来源 → 1 不是现状陈述 → 2 已确认 → 3 不是裁决 → 4 能写成枚举 `后复权/分段复权` | `canon` | 不进 `facts`：`facts` 记的是「三源 K 线取数都不是后复权」这件**另一件事** |
| 「三源 K 线取数都不是后复权」 | 0 有来源 → 1 是现状且可 grep | `facts` | 不进 `canon`：它不是「应该怎样」，而是「现在怎样」 |
| 「佣金费率现值」 | 0 有推断来源（问过 Owner，未答）→ 2 只能标假设 | `hypotheses` | 不进 `canon`：答复到达后**迁层**为 `canon`（§3.2 升级规则） |
| 「后复权 vs 现行前复权规格」冲突怎么裁 | 0 有来源 → 3 是裁决且有主体（信源优先级 + 时间） | `cases` | 不进 `canon`：`canon` 存结论值（后复权），`cases` 存「为何与旧规格冲突、怎么裁的」 |
| 「block bootstrap 要报告有效样本」 | 0/2/3 否 → 5 需流程 | `rules` | 不进 `canon`：不是一个阈值；块长（数值）则单列 `hypotheses` 待答 |

### 1.4 与 `known_unknowns.yaml` 的关系

- `known_unknowns.yaml` **不是一层**：它是「连假设都给不出」的**知识负债台账**（`config/knowledge/known_unknowns.yaml:1-20` 字段定义），由 K2 写，位于 `config/knowledge/` 根。
- 边界：能写出推断来源（`ref/`、外部资料、本波识别出的空白）→ 进 `hypotheses`；写不出来 → 进 `known_unknowns.yaml`。
- 迁移：`known_unknowns` 条目 `status: resolved` 后，若获得权威来源 → 在 `canon`/`rules`/`cases` 建新条目并在 `unknown_ref` 回指该 KU id；若仍是推断 → 进 `hypotheses`。

### 1.5 与 `openspec/specs/` 的关系（不要混）

- `openspec/specs/` 写「系统**必须做什么**」（可被 `openspec validate` 校验）；`config/knowledge/` 写「系统**知道什么**」（靠来源 + 置信度 + 判例约束）。
- **口径不进 spec 正文**（`config/knowledge/README.md:38`），否则一次口径变更会变成一次规格变更。
- 冲突处理：口径与 spec 的「来源锚点」冲突时，按信源优先级重判一次，裁决落 `cases` 层，**不手改 `openspec/specs/`**（本仓库硬约束 1：主规格只由 `openspec archive` 更新）。

## 2. 元数据 schema（一条知识的最小字段集 + 取值域）

### 2.1 必填字段（9 个）

前 6 个是机检强制（`scripts/check_knowledge_source.py:43-46`：`source / confidence / owner / strength / frequency / lifecycle`），后 3 个是本设计新增的必填（K2 采集时人工遵守，机检扩展建议见 §6）。

| 字段 | 取值域 | 含义 | 谁负责填 |
| --- | --- | --- | --- |
| `id` | `<PREFIX>-<DOMAIN>-<NNN>`，PREFIX ∈ `CAN/RUL/FAC/HYP/CAS`；NNN 三位数字；**不可复用、不可改** | 条目标识；跨波唯一；改语义 = 新 id + `supersedes` | K2 |
| `statement` | 一句话（中文），**只写口径本身，不写数值来源、不写实验数据** | 知识本体。判据：脱离上下文也能判定真假 | K2 |
| `layer` | `canon / rules / facts / hypotheses / cases`，**必须与所在目录一致** | 冗余自校验（搬文件时能发现漏改） | K2 |
| `source` | 四选一格式（见 §2.3） | 来源；`confidence=确定` 时必填且非空（机检强制） | K2 |
| `confidence` | `确定 / 假设 / 未知` | 证据等级。`确定` = 人工明确答复 或 一手材料原文；`假设` = 推断 / `ref/` / 外部资料；`未知` = 仅允许「转记 KU 前的临时态」，同波内必须迁出 | K2 |
| `owner` | `Owner`（业务方，口径/参数最终裁决）/ `product-manager`（需求口径）/ `architect`（方法与实现口径）/ `knowledge-engineer`（采集与事实维护）/ `knowledge-architect`（分层与判例归类） | 谁对这条知识的**正确性**负责（不是谁录入） | K1 指定默认，K2 落 |
| `strength` | `硬规则` / `软启发` | 约束力（定义见 §1.1） | K2（按层默认：`canon`/`rules`/`facts` = 硬规则，`hypotheses`/`cases` = 软启发） |
| `frequency` | `高` / `中` / `低` | 运行时引用热度（度量见 §3.1）。**新条目一律填 `低`**，由 K2 每波末按实测更新 | K2 |
| `lifecycle` | `proposed` / `active` / `deprecated` / `retired` | 生命周期状态（转移见 §3）。入库即 `active`；`proposed` 仅用于「已采集但未过准入」的暂存（同波内必须定稿） | K2 |

### 2.2 可选字段（按需，不填即缺省）

| 字段 | 用途 | 何时必填 |
| --- | --- | --- |
| `requirement_refs` | 支撑哪条 Requirement（如 `[R9, R10]`）或 MRD 锚点 | `canon` / `rules` / `facts` 建议填；缺省 = 未关联需求 |
| `registry_refs` | 实验台账 ID 列表（如 `[EXP-2026-11-001]`） | **`cases` 层的结论类条目必填**；其余层禁止填（防知识库变第二台账，见 §2.4） |
| `as_of` | 口径生效日 / 数据版本 / 快照时间（ISO8601 或 `rev-xxx`） | 会随时间变的口径（费率、成分股、数据口径）必填 |
| `review_at` | 下次复核日期（ISO8601） | **外部监管 / 费率 / 税率类必填**（见 §3.4） |
| `stale_after_days` | 复核过期天数（正整数） | 与 `review_at` 配套；缺省由 §3.4 的默认值兜底 |
| `supersedes` / `superseded_by` | 取代链（旧 id / 新 id） | 任何「新条目取代旧条目」必须双向填 |
| `unknown_ref` | 对应 `known_unknowns.yaml` 的 KU id | 由 KU 迁入的条目必填 |
| `scope_note` | 适用边界（如「仅回测、不适用于技术面实时信号」） | 口径被跨模块复用时建议填，防误用 |
| `notes` | 一句话补充（人工裁决原话摘要、坑说明） | 可选 |

### 2.3 `source` 格式规范（四种，机检只看非空，人看可追溯）

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 人工答复 | `人工答复:<谁>:<日期>:<主题>｜原话「…」` | `人工答复:Owner:2026-11-20:回测成本口径｜原话「佣金按…」` |
| 仓库一手材料 | `<相对路径>:<行号>｜引文「…」` | `docs/agent-team/inputs/feishu-invest-agent.md:148｜「使用后复权，或分段复权并在分红日调整」` |
| 代码/测试（仅「现在是什么」） | `<相对路径>:<行号>｜引文「…」` | `src/data_provider/tushare/fetcher.py:295｜adj="qfq"` |
| 假设来源 | `推断(基于 <来源>)` 或 `ref:<路径>@<commit>` | `ref:TradingAgents-CN@74783e8` / `推断(基于 飞书 r482 §十 未给数值)` |

**禁止**：`source` 写「见文档」「内部讨论」「众所周知」等不可复核表述；`confidence=确定` 时 `source` 为空（机检直接判 error）。

### 2.4 与实验台账（registry）的引用关系

- **方向单向**：知识条目 → 台账（`registry_refs`）。台账**不**存知识 id，它只记实验事实（假设、参数、K、区间、结果、时间戳、预注册 commit）。
- **数值不进知识条目**：收益、回撤、t 值、滑点、K 的数值只在台账。知识条目只存「口径」与「结论措辞」。理由：台账 append-only（飞书 §二·#1「跑完不许改假设，只能新开一次实验」），知识条目会随复核改写；两处都存数值必然出现双写不一致。
- **`cases` 结论类必填 `registry_refs`**：没有台账 ID 的「结论」不是结论，是印象。
- 台账被 `retired` 或知识条目退役，均不回改对方；引用失效由 `superseded_by` 表达。

## 3. 升降级与退役规则

### 3.1 频次的度量（运行时，不许拍）

- **引用事件**：某条知识被下列任一行为引用，记 1 次 —— ① 一条 Requirement / `design.md` 决策引用其 `id`；② 一次实验（台账行）按其口径执行；③ 一次人工裁决/评审引用其 `id`。
- **窗口**：**最近 3 波（wave）**。不用自然日（知识变更以波次为节拍）。
- **分档**：窗口内 ≥3 次 → `高`；1–2 次 → `中`；0 次 → `低`。
- **执行**：每波末由 K2 统计（数据源：台账 + Requirement/设计引用 + 裁决记录），T7 收口时核对。
- **红线**：**频次只能影响热度、检索优先级与「是否值得保留」，绝不能提升 `confidence`**。「很多人引用」不等于「有权威来源」——置信度只由 §2.3 的来源决定。反过来，`frequency=低` 也不构成退役理由（冷知识可能是关键约束）。

### 3.2 升级（4 条触发，谁执行）

| # | 触发 | 迁移 | 执行者 | 记录要求 |
| --- | --- | --- | --- | --- |
| U1 | 人工答复到达 | `hypotheses` → `canon` 或 `rules` | K2 | 改 `confidence=确定`、补 `source`（人工答复格式）、`lifecycle=active`、`supersedes` 回指原 HYP id |
| U2 | 台账结论被裁决为「成立」 | `hypotheses` → `cases` | K2 | 必须带 `registry_refs`；原 HYP 条目标 `deprecated` 并 `superseded_by` |
| U3 | 事实被规格/代码确认（例如「后复权成为新规格义务」） | `facts` → `canon` | K2 | 新旧两条并存：FAC 记「现在是什么」，CAN 记「必须是什么」；**不要就地改层** |
| U4 | 条目被 ≥2 条 Requirement 消费但从 `rules` 拆出了单一阈值 | `rules` → 拆出 `canon` 子条目 | K1 判定 + K2 执行 | 原 RUL 保留（方法），CAN 存阈值；两者互相 `notes` 引用 |

**反例（禁止）**：把 `hypotheses` 里「ref 借鉴来的做法」因为「用得多」升成 `canon`；把 `cases` 里的实验结论写成 `canon` 阈值（结论是「在这批样本上有效」，不是「必须执行这个数」）。

### 3.3 降级（4 条触发）

| # | 触发 | 迁移 | 执行者 |
| --- | --- | --- | --- |
| D1 | 上游口径变更（费率、税率、涨跌停幅度、指数编制规则） | `canon` → `deprecated`，新建 `canon` 条目 | K2（T7 复核） |
| D2 | 代码/规格变更使事实不再成立 | `facts` → `retired` | K2 |
| D3 | 实验证伪某假设 | `hypotheses` → `cases`（否定判例）+ 原条 `retired` | K2 |
| D4 | 出现与既有来源冲突，且新来源优先级更高 | 旧条 `deprecated` + 在 `cases` 写裁决 | K1 判定裁决，K2 执行 |

### 3.4 退役（必须有时效口径，且不许删除）

- **状态机**：`proposed → active → deprecated → retired`。**只能前进**；要复活就新建条目（`supersedes` 回指）。
- **双时钟（这是关键的时效口径）**：
  1. **波次时钟**（内生产生的知识：方法、事实、判例）—— 退役判据用「波次」：`deprecated` 连续 **2 波**无引用 → `retired`。
  2. **自然日时钟**（外部会变的口径：费率、税率、监管参数、指数规则）—— 必须带 `review_at`；未填默认「入库日 + `stale_after_days`（缺省 365 天）」。**过期未复核 → 强制把 `confidence` 降为 `假设`**（不删条目、不改 `lifecycle`），迫使消费方按「配置缺值必须拒绝执行」处理（与 R7「费率不得按 0 继续」同一条纪律）。
- **物理位置**：`retired` 条目**留在原文件**（避免断引用），标 `lifecycle: retired` + `notes` 写明退役原因；**禁止删除**（append-only 精神）。
- **只允许一个例外**：整层被方案级替换（只可能发生在评审通过的分层变更），此时整目录迁入 `<layer>/_retired/`，id 不变。
- **执行与复核**：降级/退役由 K2 执行、T7 每波收口核对、reviewer 抽查来源与状态一致性；`canon` 层的**新增**须 captain 知会（口径变更影响下游 change）。

### 3.5 状态一览（可直接拿去做机检断言）

| 字段 | 合法值 |
| --- | --- |
| `confidence` | `确定` \| `假设` \| `未知`（`未知` 不得跨波存活） |
| `strength` | `硬规则` \| `软启发` |
| `frequency` | `高` \| `中` \| `低` |
| `lifecycle` | `proposed` \| `active` \| `deprecated` \| `retired` |
| `owner` | `Owner` \| `product-manager` \| `architect` \| `knowledge-engineer` \| `knowledge-architect` |

## 4. 与代码的边界（哪些写死、哪些留人）

### 4.1 落点矩阵

| 知识类别（层） | 代码落点 | 判据 | 回测模块的例子 |
| --- | --- | --- | --- |
| `canon` 可调口径 / 参数 | **配置**：`config/app.yaml` 新增 `backtest:` 段（由 T3 落地，本波不改配置） | 会因外部变化而变（费率、税率、档位、阈值）→ 必须可改而不改代码 | 佣金率与最低额、卖出印花税率、滑点分档、门禁阈值、切点档数 |
| `canon` **不可调**不变量 | **代码**（`src/service/backtest/` 内常量或断言），**不得配置化** | 是市场规则或语义不变量，配置化等于允许「配置出 T+0」 | T+1（当日买入不可当日卖出）、封板不可成交须顺延、停牌跳过、信号不得读 t 之后数据 |
| `rules` 方法与流程 | **代码 + 单测**；其参数（块长、收缩强度等）落 `canon`/`hypotheses` | 需要算法 | block bootstrap、部分池化、三级门禁状态机、预注册校验流程 |
| `facts` 现状事实 | **不落代码**；只在知识层与评审报告里出现 | 它是「解释为什么现在做不到」的依据 | 「K 线表无成交额」「三源均为前复权」 |
| `hypotheses` 未确认 | **不落代码行为**。若实现必须预埋，只能预埋「开关 + 缺失即拒绝」，**禁止预埋默认数值** | 未经确认 | Q4 费率、Q6 切点基准、KQ-2 块长 |
| `cases` 裁决与结论 | **不落代码、不落配置**；只在 `cases` 层 + 台账引用 | 结论是「在这批样本上」的经验命题 | 「校准题复现显著跑输」「前复权冲突裁决」 |

**硬规则两条**：

1. 代码里出现任何未经 §2 来源确认的默认数值（费率、税率、阈值、档位）= 违规，评审直接打回；等价纪律已在需求侧写成 R7 Scenario「费率配置缺失时拒绝执行」。
2. 任何数值的生成/修改不得由 LLM 完成（`docs/dev/engineering-conventions.md:310`）。

### 4.2 必须保留人工确认入口的 5 处（回测模块）

| # | 事项 | 为什么不能写死 | 入口形态 |
| --- | --- | --- | --- |
| 1 | 一切费率与监管参数的**现值** | 会随政策变；写过期值比没写更危险 | `config/app.yaml` `backtest:` 段 + `review_at` 强制复核 |
| 2 | 门禁判据（「不劣于基准」「方向一致」） | 是经营决策，不是技术参数 | `hypotheses` 条目 → 答复后 `canon` |
| 3 | 软标签判定（主题 / 产业链 / 管理层评价） | 主观、事后可变 | `hypotheses` 层登记（标签 + 时间 + 理由）+ 半年回看 |
| 4 | 校准失败后的处置（修台子 / 换口径 / 停用） | 需要人判「修什么」 | `cases` 裁决 + Owner 签署 |
| 5 | 样本外烧毁的例外批准 | 一旦自动化就等于没有「只跑一次」 | 台账留痕 + 人工批准者字段 |

### 4.3 知识层与 `src/` 的耦合纪律

- 知识条目**不得**引用类名/函数名/表名作为「口径」依据（那是 `facts` 的证据形式，不是口径本身）；反过来，代码注释**可以**引用知识 id（`# 见 CAN-COST-001`），但注释不是知识真源。
- `fact` 类条目随代码变更退役，因此**不要**在 `canon`/`rules` 的 `source` 里只写代码行号（代码行号会漂移）——代码行号只允许出现在 `facts`。

### 4.4 「就地改」禁令

任何条目改语义（不是改格式）都必须：新建条目 + 旧条 `deprecated` + 双向 `supersedes`。理由：`registry_refs`、Requirement 引用、代码注释都按 id 指过来；就地改会让历史引用指向另一条知识。

## 5. 被否的分层方案（3 个，含否决理由与复活条件）

### 否-A：按数据域 / 代码模块分层（`market-data` / `financial` / `matching` / `statistics` / `gate`）

- **理由**：
  1. **同一条知识会跨域重复**：复权知识既属「行情」也属「撮合成本」，公告日对齐既属「财务」也属「无未来函数」——重复登记必然出现两处漂移，而知识库最怕的就是「两处口径不一致」。
  2. **按域分层回答不了「能不能写死」**：本设计最核心的判据是「是否确定性、是否需要人确认」，数据域与这条判据正交，导致「该写死还是该留接口」还得逐条再判一次。
  3. **与代码生命周期错配**：`config/knowledge/README.md:4` 明确「代码随 change 归档，知识跨波存活」；按模块分层会让 `src/` 一次重构就要求知识层重排（`docs/dev/engineering-conventions.md:107-131` 的子域清单本身还在增长）。
- **复活条件**：若某天知识条目数量到千级、且出现了「同一口径在不同域有不同合法性」的证据，可先加 `domain` 字段（本设计已有可选字段位）而不是换分层。

### 否-B：单层平面清单（全部条目进一个 `entries.yaml`，只靠 `confidence` 区分）

- **理由**：
  1. **无法表达「同为确定、退役机制不同」**：`facts`（代码一改即退役）与 `canon`（口径变了才退役）都是 `确定`，平面方案只能给两者打同一个标签，退役规则无法落地。
  2. **升降级失去目标层**：没有层，所谓「升级」只剩改一个字段值，等于把语义塞进枚举，评审无法判断「这次升级对不对」。
  3. **准入无法机检**：「强度 × 频次」两维读不出来，`scripts/check_knowledge_source.py` 只能查字段存在与否，查不出「这条本该是事实却被当口径用」——历史上这正是最容易出的错（`config/knowledge/README.md:23`）。
- **复活条件**：条目数 < 20 且只有单一能力消费时，平面清单的维护成本更低。本项目已确定会跨多个 change 累积（回测是第一个），不满足。

### 否-C：按置信度分层（`certain/` · `assumed/` · `unknown/`）

- **理由**：
  1. **置信度是可变量，不是容器**：升级/降级会让条目**搬家**，`registry_refs`、Requirement 引用、代码注释里的 id 全部要跟着改 → 引用稳定性归零。
  2. **`unknown` 不属知识**：`config/knowledge/known_unknowns.yaml` 已经承担「未知」台账，再分一层等于同一件事两处登记。
  3. **把「事实」与「口径」混在一层**：两者同为 `确定`，却一个必须退役、一个必须遵守，混层后评审无法判断某条能不能被引用为约束。
- **复活条件**：不复活。置信度作为**字段**（§2.1）已经足够，层应表达生命周期与约束力。

### 6.2 建议的机检扩展（本波不写代码，登记给 T3/T8）

现有 `scripts/check_knowledge_source.py` 只校验六字段 + 置信度枚举 + 「确定必须有来源」。本设计新增的必填字段与状态机**尚无机检**，建议下波补三条断言（写在脚本或评审清单里）：

1. `id` / `statement` / `layer` 存在且 `layer` 与所在目录一致；
2. `lifecycle` ∈ 四值；`lifecycle=retired` 时 `notes` 必须写退役原因；
3. `cases` 层 `confidence=确定` 的结论类条目必须带非空 `registry_refs`；`canon`/`rules`/`facts` 层出现 `registry_refs` 报 warning。
