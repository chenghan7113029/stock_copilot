# Case 标注模板（`docs/cases/<case-id>/annotations.md`）

> 用途：把**一个真实发生过的分析案例**记成可被流程消费的现实锚点。
> **标注区（本文件）**归 product-manager 主笔（「用到的知识」列与「知识差距」段归 knowledge-architect）；
> **溯源区（`traces.yaml`）**归 qa 只 append。两份文件职责不重叠。
>
> 铁律：**能引用的一律不转述**——run 目录名、数字、判定结论只写「见 `traces.yaml` 第 N 条」，不在本文件手抄一遍。

## 0. 元信息

| 项 | 内容 |
| --- | --- |
| 案例 ID | `<case-id>`（kebab-case，与目录同名） |
| 来源 | 谁 / 何时 / 什么场景（可指到文件、对话、报告路径） |
| 原始业务问题 | 原话照抄，不改写成「需求」 |
| 我的产品现在能不能做 | 能 / 部分 / 不能 + 一句话理由 |
| 最终结论 | 案例给出的结论（若有） |
| ground-truth | 采纳 / 存疑 / 不采纳 — **只能由业务方标**，PM 不替判 |
| 标注日期 | `<YYYY-MM-DD>` |

> **没有 ground-truth 的 case 只能当「方法参考」，不能当 case 回归（K3）的验证标准。**
> 「不知道 / 不记得」是合法答案：缺哪部分，就把本 case 降级为 partial / 方法参考，并在此注明。

## 1. 分析链逐环拆解（PM 只拆**功能**）

沿本仓库分析链逐环问两个问题：① 案例里实际做了什么动作 ② 我的产品现在能复现吗（能 / 部分 / 不能）。
**「用到的知识」列由 knowledge-architect（K1）填，PM 留空。**

| 环 | 案例实际做了什么 | 用到的知识（K1 填） | 用到的能力（代码 / 模块） | 产品现状 | 差距 |
| --- | --- | --- | --- | --- | --- |
| 提问（要回答什么） | | | | 能 / 部分 / 不能 | |
| 取数（数据从哪来、什么口径） | | | | | |
| 计算（指标 / 归因 / 筛选规则） | | | | | |
| 结论（怎么判、阈值是什么） | | | | | |
| 呈现（怎么给人看） | | | | | |

> 分析链随 MRD 演进，环名可改；环数变了要在「来源」里注明依据（哪版 MRD / 哪份设计）。
> 「产品现状」必须**可证伪**：写「现有 specs / 代码里没有 X」要指得到位置（`openspec/specs/<cap>/spec.md` 或 `src/...:行`），禁止「感觉缺」。
