# Case 拆解模板（PM 在 T1 使用）

> 用途：PM 拿 case 当"现实切片"，沿本仓库分析链逐环做**功能差距分析**，拆出"我的产品缺什么**能力**"。
> **知识缺口识别（用了什么知识、库里有没有）是 knowledge-architect（K1）的活，不在此模板填**；
> 本项目没有可蒸馏的飞书机器人 / 飞书号，K1 的口径确认一律**问人**（经 captain 转交）。
> 产出物：本文件落 `openspec/changes/<change>/case-teardown.md`；业务事实同步回填
> `docs/cases/<case>/annotations.md`（标注区），**不写 `traces.yaml`**（溯源区归 QA）。

## 0. case 元信息

| 项 | 内容 |
| --- | --- |
| 案例 ID | `<case>`（kebab-case，与 `docs/cases/<case>/` 目录同名） |
| 来源 | 谁、何时、什么业务（出处：文档链接 / 对话记录 / 报告路径） |
| 原始业务问题 | 原始话术，不改写 |
| 数据窗口 | 标的 + 时间范围（如「600519，2026-08-01 至 2026-08-31」），供复现时对齐 |
| 最终结论 | case 的结论（原文或忠实转述） |
| 结论编号 | `C1 / C2 / …`：与 `annotations.md` 的结论编号、`traces.yaml` 的 `conclusion` 字段对齐 |
| ground-truth | 采纳 / 存疑 / 不采纳（**只能由业务方标注**，PM 只问不填） |

> **无 ground-truth 的 case 只能当"方法参考"，不能当 case 回归的验证标准。**
> PM 不得替业务方判断结论对错，也不得凭"看起来合理"补一个 ground-truth。

## 1. 分析链逐环拆解（PM 只拆功能）

> **本仓库分析链：提问 / 取数 / 计算 / 结论 / 呈现（随 MRD 演进改）。**
> 选它的理由：`docs/mrd/mrd-v1.md` 当前仍是骨架（§1.1–§5.1 全是 `<...>` 占位），没有可沿用的
> 现成分析链；`docs/mrd/product-overview.md` 只有产品级流程（交易前/中/后），不能直接当逐环拆解对象。
> 等 MRD §1.1/§3 落定真正的分析链后，**替换本节表格的环定义**，其余列不变。

每环问两个问题（PM）：① case 实际做了什么动作 ② 我的产品现在能复现吗（能 / 部分 / 不能）。
**「用到的知识」列由 K1 填，PM 不填。**

| 环 | case 实际做了什么 | 用到的知识（K1 填） | 用到的能力 | 产品现状 | 差距 |
| --- | --- | --- | --- | --- | --- |
| 提问（Question） | | | 意图 → 标的/维度定位 | 能/部分/不能 | |
| 取数（Data） | | | 数据源适配 + 本地库 | | |
| 计算（Calc） | | | 确定性计算（指标/评分/估值/信号） | | |
| 结论（Conclusion） | | | 综合信号、红蓝对抗、Checklist 拦截 | | |
| 呈现（Presentation） | | | 报告输出（CLI / HTML / 推送） | | |

> 能力落点提示（填「用到的能力」列时按仓库真实位置写，别写"分析模块"这种含糊词）：
> `src/apps/`（CLI 子命令）、`src/controller/`（接口）、`src/service/`（技术面/价值面/情绪面/报告）、
> `src/data_provider/`（tushare / baostock / akshare 适配）、`src/dao/`（SQLAlchemy 读写）。

## 2. 功能需求（spec delta）

| 能力 | 支撑 case 哪一环 | 产品现状（可证伪） | 需求 |
| --- | --- | --- | --- |
| | | | |

> 「产品现状」写**可被证伪的证据位置**，例如：
> `openspec/specs/<capability>/spec.md` 里没有该 Requirement / `src/service/<文件>.py:120` 只做了 A 没做 B /
> `python -c "..."` 跑不出该字段。**禁止写"感觉缺"**。

## 3. 硬规则

1. 每条功能差距的「产品现状」必须**可证伪**——"现有 specs 里没有 X"要指得到位置，禁止"感觉缺"。
2. 每条功能需求都能指回 case 的某一环（本仓库 5 环之一），指不回去的不许进 proposal。
3. 遇到"这不是能力问题、更像缺知识"的缺口，标「**疑似知识缺口，待 K1 确认**」，
   **不自己蒸馏、不自己判知识/功能**；也不填「用到的知识」列。
4. 判据自检（advisory）：代码能不能补上这个缺口？能 → 功能；不能 → 疑似知识缺口，标出来留给 K1。
5. ground-truth 只由业务方标注；未标时在元信息写 `partial` 并说明缺什么，不得自己拍一个。
6. 本文件**不抄 trace 数字**（数字、verdict 归 `docs/cases/<case>/traces.yaml`）：这里只写结论编号 +
   「见 traces.yaml」。引用 MRD 锚点写编号（`MRD-3.1` / `product-overview §5.1.2` 之类），不整段转述。
