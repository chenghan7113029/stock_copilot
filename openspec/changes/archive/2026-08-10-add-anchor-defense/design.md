## Context

`ValuationAggregator._price_percentile()`（`src/service/value/aggregator.py:198-202`）已实现：

```python
def _price_percentile(price: float, low: float, high: float) -> float:
    if high <= low:
        return 50.0
    pct = (price - low) / (high - low) * 100
    return max(0.0, min(100.0, pct))
```

即当前价格在多方法聚合估值区间 `[low, high]` 中的线性百分位，`ValueAnalyzer._analyze_stock()` 将其写入 `ValueAnalysisResult.price_percentile`，`format_value_report()` 直接以 `"价格分位: {X}%"` 的形式展示。这条链路已经完整交付，本 change **不重新计算任何数值**，只处理"这个数字应该以什么形态呈现给用户"。

需要区分两个概念：
1. **`price_percentile`（已存在）**：当前价格相对于**多方法估值聚合区间**（一个横截面的、基于当前基本面数据的估值分布）的位置——衡量的是"贵不贵"。
2. **MRD 设想的"未来 1 年胜率 60% 区间"（不存在）**：基于历史统计（如"过去当价格处于类似估值分位时，未来 1 年上涨概率/收益分布"）的前瞻性区间——衡量的是"过去处于类似位置后，统计意义上大概率会怎样"。这是一个真正的新计算（需要历史价格 + 历史估值序列的回测型统计），工作量与风险显著高于呈现层调整。

`agent-engineering-quality.md` 三角权衡（鲁棒性 > 稳定性 > 消耗）提示：新增一个未经历史回测验证的"胜率"数字，如果计算方法不严谨，反而会制造一个新的、看似精确实则脆弱的锚点，与"锚定防御"的初衷相悖。因此本 change 选择先把"防御"这一层（不暴露原始锚点数字、把已有分位数字包装为防御性的定性表达）做扎实，把"真正的前瞻胜率统计"列为需要独立立项、需要历史数据验证的后续工作。

技术面 `IndicatorCalculator._analyze_support_resistance`（`src/service/tech/calculator.py:329-333`）目前只计算近 20 日高点作为 `resistance_levels`，不是长期意义上的"历史最高价"（用户日常语境下的"历史最高价"通常指上市以来或至少 1 年以上的最高价，是最容易被当作心理锚点的数字）。当前系统里这个数字**完全不存在**，因此"隐藏"这件事目前是空对空——本 change 需要先让这个数字存在（否则无法验证"隐藏规则"是否生效），但存在的同时立即建立默认隐藏的呈现护栏。

## Goals / Non-Goals

**Goals:**
- 将已有的 `price_percentile` 数值包装为定性分档描述，弱化具体数字在报告中的视觉/语义焦点
- 新增"历史最高价"计算（基于本地 K 线缓存），但默认不在任何报告输出中展示
- 建立"任何绝对价格锚点类字段，默认不在报告中展示，需显式 opt-in flag 才展示"的呈现护栏惯例，供未来功能（尤其是成本价相关）复用
- 保持向后兼容：`--json` 输出仍包含原始 `price_percentile` 数值（程序化消费方/未来 Web 前端需要原始数值做进一步处理），"隐藏"只针对**默认文本呈现**，不阉割数据本身

**Non-Goals:**
- 不实现基于历史回测的"未来 N 年胜率区间"统计模型（不预先设计其算法、数据需求、回测方法论——这是一个显著更大的、需要独立验证历史数据可得性与统计方法有效性的课题，留待后续视 V1 使用反馈决定是否立项）
- 不处理用户买入成本价/持仓盈亏的隐藏（因为该数据当前不存在，`add-fresh-entry-check` 尚未实现；本 change 只为"未来实现成本价隐藏"预留可复用的护栏惯例与代码模式，不在本 change 内消费任何持仓数据）
- 不修改 `ValuationAggregator._price_percentile()` 的计算公式（沿用既有实现，纯呈现层改动）
- 不新增数据库表（历史最高价从 `Kline` 表现有数据实时计算，不持久化衍生结果）

## Decisions

### 决策 1：`price_percentile` 是否需要重新计算——不需要，直接复用

**选择**：确认 `price_percentile` 语义（估值区间内的相对位置）已经是一种"模糊区间概率化表达"的雏形，本 change 直接复用该字段，新增的工作是**呈现规则**：把数值映射为定性分档描述作为呈现主体。

**理由**：见 Context 部分的调研结论。重复造一个"新的价格百分位"字段是明确的重复造轮子，`docs/agent-engineering-quality.md` §6.1"可固化为代码的任务识别"原则同样适用于"设计任务"层面——已有能力应优先复用而非重新发明。

**备选方案**：新增一个独立的"锚定防御专用百分位"字段，与 `price_percentile` 并存——拒绝，会造成两个语义相近但计算口径不同的字段同时存在于 `ValueAnalysisResult`，增加使用者的认知负担和未来维护成本；如果未来确实需要"基于历史回测的胜率区间"（与当前 `price_percentile` 语义不同），应该用一个语义清晰区分的新字段名（如 `forward_return_percentile_band`），而不是"锚定防御版 price_percentile"，且应作为独立 change 提出（见 Open Questions）。

### 决策 2：分位定性分档映射——5 档描述，阈值与既有 `_assessment_from_mos` 风格对齐

**选择**：新增 `src/service/value/anchor.py::percentile_band(price_percentile: float) -> str`，映射规则：

| `price_percentile` 区间 | 定性描述 |
|---|---|
| `< 20` | 历史估值区间低位 |
| `20 ~ 40` | 历史估值区间中低位 |
| `40 ~ 60` | 历史估值区间中性 |
| `60 ~ 80` | 历史估值区间中高位 |
| `> 80` | 历史估值区间高位 |

`format_value_report()` 呈现顺序调整为：先展示定性描述（如"当前价格处于历史估值区间中高位"），数值以括号形式弱化标注（如"(分位 72%)"），而不是像现在这样以"价格分位: 72%"这种把数字放在前面、作为句子主语的形式呈现。

**理由**：定性优先的呈现方式让用户先接收"相对位置"这个模糊判断，而不是先锚定在一个精确数字上；阈值分档沿用 `aggregator.py::_assessment_from_mos()` 已经验证过的"5 档制"风格（低估/合理偏低/合理/合理偏高/高估），保持代码库内一致的分档粒度习惯，不引入新的分档哲学。

**备选方案**：只做纯定性描述，完全不展示数值——拒绝，`--json` 场景与部分用户仍需要精确数值做进一步分析（如自己画图表），"隐藏"应理解为"不作为默认呈现的焦点"而非"彻底删除信息"，完全隐藏数值属于过度设计且可能引发用户对"黑箱评分"的不信任。

### 决策 3：历史最高价的计算范围与隐藏机制

**选择**：`src/service/value/anchor.py::historical_high(code, window_days=None) -> float | None`，从本地 `Kline` 表读取该 `code` 全部可得历史（`window_days=None` 时不限窗口，取本地缓存范围内最大 `close`/`high`），纯离线计算（不联网，K 线数据依赖已有 `sync` 命令拉取的缓存）。该函数默认**不会**被 `report value`/`report tech`/`report dual` 的默认输出路径调用；仅当 CLI 显式传入 `--show-anchor-price` flag 时才计算并展示，且展示时附加固定提示："⚠ 历史最高价仅供参考，不建议以此作为买卖决策的心理锚点"。

**理由**：
- 落地"隐藏易锚定数字"的产品要求需要有一个具体、可测试的隐藏对象；`resistance_levels`（近 20 日高点）语义上不是用户心理学意义上的"历史最高价"（通常指数年维度），故新增专门函数，语义清晰。
- 默认隐藏 + opt-in 展示 + 强制警示文案的三段式设计，形成一个可被未来其他"锚点类"字段（如未来的成本价）复制的固定模式，本 change 的核心交付物之一就是确立这个模式（而不仅是这一个字段本身）。
- 纯离线、不新增持久化：历史最高价是"从已缓存 K 线派生的只读视图"，没有必要额外存表，符合"确定性计算无需重复存储可推导数据"的一般工程原则，也避免了本 change 引入数据库 migration 的复杂度。

**备选方案**：
- 默认展示历史最高价但用较小字号/次要位置弱化（视觉层面弱化而非默认隐藏）——拒绝，CLI 是文本终端，没有"字号"这个视觉手段可用；即使未来做 Web UI，"默认不显示、需要用户主动展开"仍然是比"永远显示但弱化"更强的防御，故选择更保守的默认隐藏。
- 不实现历史最高价计算，只写文档说明"未来实现时应遵循默认隐藏原则"——拒绝，纯文档约定没有可验证性（无法写单测断言"默认不展示"），本 change 选择用一个真实可测试的最小实现来落地并验证这个护栏模式是可行的。

## Risks / Trade-offs

- **[风险] "定性分档优先"的呈现方式改变了 `report value` 既有文本输出格式，可能破坏依赖该输出格式做正则解析的下游脚本（如果存在）** → **缓解**：仓库内检索确认目前没有对 `report value` 文本输出做正则解析的下游消费方（`--json` 才是程序化消费的推荐路径，且 `--json` 输出保持 `price_percentile` 原始数值字段不变，不受本 change 呈现规则影响）；`test/apps/test_cli_report.py` 已有针对文本格式的快照式测试，需要在本 change 中同步更新预期文本。
- **[风险] "历史最高价"从本地 K 线缓存计算，若用户从未 `sync` 过足够长历史的 K 线（`kline_days` 配置默认仅 90 天），计算出的"历史最高价"实际只是"近 90 天最高价"，与用户心理预期的"历史最高价"（可能是数年）不符，可能造成误导性的虚假安全感** → **缓解**：`historical_high()` 展示时的固定提示文案明确注明所依据的时间窗口（如"（基于本地缓存 XX 天数据）"），不得让用户误以为是全历史最高价；若本地缓存不足 1 年，追加"数据窗口不足 1 年，历史最高价仅供参考"的额外警示。
- **[风险] 默认隐藏可能被用户认为是"藏着掖着不给看关键信息"，产品体验上有争议** → **接受**：这正是 MRD 明确要求的产品哲学（"隐藏易锚定数字"是显式的产品决策，非工程默认保守选择），`--show-anchor-price` opt-in 机制保证用户仍可主动查看，不是彻底不可得。
- **[风险] 分位定性分档的阈值（20/40/60/80）与 `_assessment_from_mos` 的阈值（20/5/-5/-20）不是同一套坐标系（一个是 0-100 的 percentile，一个是 -N% ~ +N% 的 margin of safety），两套五分档可能在同一份报告里同时出现造成用户混淆（如"合理偏高"+"历史估值区间中高位"看起来像重复信息）** → **缓解**：呈现层需清晰区分两者语境（`assessment` 回答"贵不贵/相对公允价多少折价"，`percentile_band` 回答"当前价格在估值区间内的相对位置"），在报告文本中用不同的前缀/小节区分（如"评估: {assessment}" 与"锚定位置: {percentile_band}（分位 {X}%）"分行展示，不合并成一句话），单测中覆盖典型组合的期望文本，避免歧义。

## Migration Plan

- 纯呈现层改动 + 新增只读计算函数，无数据库变更，无需 migration
- `format_value_report()` 文本格式变化仅影响文本模式输出；`--json` 输出结构不变（新增字段除外，向后兼容）
- 回滚：还原 `formatters.py`/`cli.py` 改动、删除 `src/service/value/anchor.py` 即可，不影响价值面既有计算逻辑（`aggregator.py` 未被修改）

## Open Questions

- 是否需要独立立项"基于历史回测的前瞻胜率区间"（真正对齐 MRD 字面意思的"未来 1 年胜率 60% 区间"）？—— 本 change 不做决定；建议在 V1（本 change）交付后，根据用户对当前"定性分档"呈现方式的实际反馈，评估是否值得投入历史回测统计的工作量（需要验证历史 `historical_pe`/`historical_pb` 序列的覆盖年限是否足够支撑有意义的统计样本）。
- 成本价隐藏规则的具体交互（如"默认隐藏成本价，用户需二次确认才能查看盈亏"）留给 `add-fresh-entry-check` 设计时决定，本 change 只承诺"届时应复用本 change 建立的默认隐藏+opt-in+警示文案三段式模式"，不预先设计 `add-fresh-entry-check` 的具体字段。
- `--show-anchor-price` 是否应该是全局配置（`config/app.yaml`）而非每次调用的 CLI flag？—— V1 选择 CLI flag（更符合"每次显式声明我要看锚点数字"的防御哲学，全局配置容易被设置一次后遗忘从而失去防御意义），若未来 Web 阶段有更好的交互方案（如每次查看前的二次确认弹窗）可以重新设计，不受本 change 约束。
