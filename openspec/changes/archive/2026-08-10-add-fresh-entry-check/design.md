## Context

`product-overview.md` §5.2 PO-05「假设今日首开仓」要解决的认知偏差是沉没成本谬误：「持仓被套，犹豫是否加仓」时，用户容易被已投入的成本锚定，而不是理性评估「如果今天从零开始，这笔钱还要不要买这只股票」。产品机制是：**隐藏**成本价与浮盈浮亏百分比，只呈现现价 + 三维分析，强制用户用「无仓位」的框架重新思考。

当前仓库没有任何「用户持仓」概念——`src/dao/models.py` 里没有持仓表，`StockSnapshot`/`Kline` 都是行情快照缓存，不是用户的个人持仓记录。要实现「隐藏成本价」，前提是**先有**成本价可以隐藏，因此本 change 隐含一个前置依赖：一个最小化的持仓记录数据模型。

## Goals / Non-Goals

**Goals:**
- 提供最小化持仓记录数据模型（`code`/`cost_price`/`shares`/`opened_at`），只服务于「隐藏成本价重新评估」这一个场景
- 提供 CLI 录入命令，让用户能录入/更新持仓成本价
- 提供 `entry-check` 命令：复用既有 `DualTrackAnalyzer.analyze_offline()` 的确定性结果，呈现时不包含成本价与盈亏%，改用「若无仓位，现价是否仍值得买入」的框架提问
- 用户自行在 CLI 会话中回答「是/否」，「否」时输出提醒文案（非自动交易动作）

**Non-Goals:**
- 不做完整持仓管理系统（加仓历史、多次成交流水、自动盈亏计算展示、批量持仓看板均不做）
- 不做定时/后台调度（无 cron/scheduler 基建）
- 不持久化用户对框架提问的「是/否」回答
- 不依赖 `add-decision-checklist`（两者可独立实现、独立使用）
- 不做 Web 展示（等待 REST API 就绪）

## Decisions

### 决策 1：持仓表——本 change 顺带建最小表，不拆出独立的 `add-position-tracking` change

**选择**：在本 change 内新增 `PositionRecord` 表，字段严格限定为 `code`（唯一）/`cost_price`/`shares`/`opened_at`/`updated_at` 五个字段，通过一个新增的 `position-tracking` capability（而非拆分成独立 change）承载。

**理由与备选方案权衡**：

| 维度 | 选项 A：本 change 顺带建表（选择） | 选项 B：拆出 `add-position-tracking` 独立 change |
|---|---|---|
| 立项成本 | 低——一次 propose 即可覆盖数据模型 + 使用场景 | 高——需要先完整走一遍 4 文件 OpenSpec 流程 for 一个只有 5 个字段的表 |
| 需求耦合度 | 高——持仓表在 MRD 中没有独立的产品叙事，只在 PO-05 场景下被提及，脱离 `entry-check` 场景讨论"持仓表该长什么样"缺乏具体约束 | 低——但正因为缺乏具体约束，容易导致过度设计（如脱离场景就开始设计加仓历史、成交明细等 V1 不需要的字段） |
| 未来复用性 | 若 `add-decision-checklist`、Checklist 表未来也要引用持仓——本 change 的 `position-tracking` capability 已作为独立 capability 存在于 `openspec/specs/`，未来 change 可直接在 proposal 中引用/修改它，不因为"顺带建"而无法被复用 | 理论上更"干净"，但收益在 V1 阶段不明确（YAGNI） |
| 与 MRD 优先级对齐 | PO-05 是 P0，尽快交付；不引入额外的立项排队环节 | 需要先完成一个不在 roadmap 中显式列出的新 ID 的 change，拖慢 PO-05 交付 |

选择选项 A，但**严格控制字段范围**（决策的核心约束）：只做「一个代码对应一条当前持仓」的覆盖式记录，不做任何形式的持仓历史/多次成交追踪，避免"顺带建表"演变成"顺带建一个完整持仓管理系统"。

**理由**：`docs/mrd/roadmap-todo.md` 中没有独立的「持仓管理」ID，说明这不是产品当前阶段的一等需求，只是 PO-05 的技术前提；拆出独立 change 会制造一个 MRD 中不存在对应叙事的「野生」capability，容易在缺乏具体使用场景约束的情况下过度设计字段（如要不要支持多次加仓、要不要算加权成本价等）。绑定在 `entry-check` 场景下设计，字段范围天然被"够用就好"约束住。

### 决策 2：持仓覆盖式存储——一个代码只保留一条当前持仓

**选择**：`PositionRecord.code` 唯一索引，`position set <code> --cost <price> --shares <n>` 是 upsert 语义（存在则更新 `cost_price`/`shares`/`updated_at`，不存在则插入并记录 `opened_at`）。不支持同一代码多条持仓记录（如分批建仓的每一笔）。

**理由**：`entry-check` 场景只需要"当前这笔仓位的成本价是多少"这一个聚合值，不需要知道具体分几笔买入。用户如果分批加仓，`cost_price` 由用户自行折算为加权平均成本后录入（V1 不提供自动加权计算，是"最小化"字段范围的直接体现）。

**备选方案**：支持多条持仓记录（每次 `position set` 追加一行,取最新或加权平均）——拒绝，这就是决策 1 里要避免的"演变成完整持仓管理系统"的第一步；一旦支持多条记录，就需要决定如何聚合成本价，功能复杂度显著上升，而 PO-05 场景并不需要这种精细度。

### 决策 3：触发机制——手动 CLI 命令，不做定时调度

**选择**：`entry-check <code>` 是用户手动触发的 CLI 命令，内部直接调用 `DualTrackAnalyzer.analyze_offline()`（不依赖尚未实现的 `add-stock-dashboard`，避免引入 change 间的实现顺序依赖），呈现时：
- 输出现价、价值面结论（估值区间/评级，**不输出**安全边际百分比与持仓浮盈浮亏，因为百分比类字段最容易被用户用来反推成本价）
- 输出技术面结论（趋势、信号）
- 输出框架提问：「若你今天没有 <code> 的仓位，以现价 <current_price> 买入，你还会买吗？」
- 若本地有该代码的 `PositionRecord`，命令末尾追加固定提醒：「以上评估已隐藏你的实际成本价，请基于当前信息独立判断，不要被已投入的成本影响决策」；若本地无持仓记录，则跳过该提醒（因为没有「隐藏」的必要，直接说明"未检测到本地持仓记录，以下为标准三维分析"）

「定期」由用户自行决定重复运行频率（如每周），本 change 不提供任何提醒/调度机制。

**理由**：当前仓库没有任何后台任务/调度基建（无 Celery、无 cron 集成），引入调度器是与 PO-05 核心价值（隐藏成本价的呈现框架）无关的额外基建，且个人使用场景下用户自己记得定期运行的成本远低于开发一套调度系统。不依赖 `add-stock-dashboard` 是为了让本 change 可以独立于该 change 的实施进度交付（两者都是 P0，谁先完成不应互相阻塞）。

**备选方案**：
- 依赖 `add-stock-dashboard` 的 `DashboardBuilder`——拒绝，两个 change 均为 P0 且无强制顺序要求，若互相依赖会在其中一个未完成时阻塞另一个；直接调用更底层的 `DualTrackAnalyzer.analyze_offline()` 是两个 change 都在用的公共基础，不构成新依赖
- 在 `sync` 命令末尾自动触发 `entry-check` 提示——拒绝，`sync` 是纯数据同步命令，混入决策护航的呈现逻辑违反单一职责，且不是所有 `sync` 场景都有对应持仓（大部分自选股不持仓）

### 决策 4：不持久化用户的「是/否」回答，与 Checklist 的持久化职责边界区分

**选择**：`entry-check` 命令输出框架提问后，若用户在后续对话/操作中回应「否」，命令**不会**记录这个回答到任何数据库表；只在当次 CLI 输出中给出提醒文案（如「若你的答案是『否』，建议重新评估当前仓位是否需要减仓/止损，可运行 checklist submit 记录你的正式决策」）。

**理由**：`add-decision-checklist` 已经承担「强制留痕」的职责（决策护航的正式审计记录）；`entry-check` 的定位是一个轻量的「自我提问工具」，帮助用户在决策前先想清楚，而不是决策留痕系统本身。如果两者都做留痕，会产生功能重叠——什么算「正式决策记录」会变得模糊（是提交 Checklist 才算，还是 entry-check 回答"否"也算？）。保持 `entry-check` 无持久化，明确「留痕」只有一个入口（Checklist），职责边界清晰。

**备选方案**：`entry-check` 也持久化用户回答（新增 `EntryCheckLog` 表）——拒绝，会与 `ChecklistRecord` 产生语义重叠（两者都可能记录"用户在某个时间点对某只股票的某种决策倾向"），未来做复盘归因（PO-09）时无法明确该以哪个表为准；且 `entry-check` 本身也不强制用户"回答"（CLI 无法强制捕获交互式的自由回答并结构化存储，除非引入额外的 prompt 输入流程，这与决策 3"轻量提问工具"的定位相悖）。

## Risks / Trade-offs

- **[风险] 决策 1 选择"顺带建表"，若未来产品需要更完整的持仓管理（多次加仓、批量持仓看板等），`PositionRecord` 的最小字段设计需要推倒重来** → **接受**：这是「先能用、再完整」既定实施原则下的合理取舍；`code` 唯一约束的表结构变更成本可控（加字段、放宽唯一约束均是非破坏性 schema 演进），届时可作为独立 change（可以是当初讨论过的 `add-position-tracking` 升级版）处理。
- **[风险] `entry-check` 隐藏了盈亏百分比，但用户仍可能通过"现价 + 记忆中的大致成本"心算出大概盈亏，隐藏效果有限** → **接受**：这是产品机制本身的固有局限（无法阻止用户脑内心算），`product-overview.md` §5.2 的机制设计初衷是"减少呈现层面的锚定强化"，不是"让用户完全遗忘成本"，V1 按 MRD 字面要求实现即可，不追求心理学意义上的完全绕过锚定效应。
- **[风险] 未录入持仓的代码运行 `entry-check` 时，命令退化为"没有隐藏意义的普通三维分析摘要"，与 `report summary`（`add-llm-comprehensive-report`）功能重叠** → **接受**：属预期行为（决策 3），且提示文案会明确说明"未检测到本地持仓记录"，用户能理解这不是本命令的主要使用场景；不因此禁止未录入持仓时运行命令（禁止会增加不必要的前置校验负担）。

## Migration Plan

- 数据库变更：新增 `position_records` 表（`PositionRecord`），通过 `Base.metadata.create_all()` 自动建表；`ensure_sqlite_schema()` 补充兜底建表逻辑
- 纯新增，不影响任何既有表或既有命令行为；不依赖 `add-decision-checklist`/`add-stock-dashboard` 的实施进度
- 回滚：删除 `src/service/guard/fresh_entry_check.py`、`src/dao/position_repo.py`、`PositionRecord` ORM 定义、CLI 中 `position`/`entry-check` 子命令即可；已建表若有数据，回滚时保留表结构，不做破坏性 `DROP TABLE`

## Open Questions

- 未来若持仓管理需求变得复杂（多次加仓、批量看板），是否需要把 `PositionRecord` 迁移到独立 change 重新设计——本 change 不预先规划迁移路径，等真实需求出现时再评估（YAGNI）。
- `entry-check` 是否应该在检测到「强势下跌 + 有持仓」等高风险组合时主动提高提醒强度（如加粗警告）——V1 统一使用同一套提醒文案，不做风险分级展示，留待未来根据实际使用反馈决定是否需要分级。
